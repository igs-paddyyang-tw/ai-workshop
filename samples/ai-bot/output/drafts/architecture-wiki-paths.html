🔍 Wiki 取用路徑分析

kiro-cli vs WikiEngine — Bot 對話時如何取得知識庫資料

📐 整體架構

使用者 TG 訊息 ↓ handlers.py handle_message() ↓ ┌─ L1: /reset → 清空 session ├─ L2: /skill_id → 直接執行 Skill ├─ L3: keyword → Planner 路由 └─ L4: 進入主對話處理 ←── 這裡觸發 Wiki ↓ ┌────┴────┐ ↓ ↓ 4a. 4b. 4c. 4d. kiro-cli WikiEngine Memory Gemini (優先) (fallback) Search fallback

🔀 兩條路徑詳解

路徑 A：kiro-cli 優先

觸發：系統有裝 kiro-cli

  • spawn kiro-cli 進程
    cwd = agents/market-agent/
  • kiro-cli 載入 SOUL.md + SKILL.md
  • AI 自行判斷是否需要讀 wiki
  • 用 read 工具讀 knowledge/*.md
  • 用 glob 工具搜尋檔案
  • 可能用 web_search 搜外部
  • 組合資訊 → stdout 輸出
  • process.py 收 → _clean_output()
特點：獨立 LLM 進程，有完整工具鏈，品質最高但速度慢（30-120s）

路徑 B：WikiEngine Fallback

觸發：kiro-cli 沒裝或沒回覆

  • 建立 WikiEngine(agent_id="market")
  • _tokenize(q) → bigram 中文分詞
  • 搜私有 wiki → 搜全域 wiki
  • 逐檔 rglob("*.md") 全文比對
  • 取 title + snippet（200 chars）
  • _rag_answer() → Gemini API
  • 回傳 answer + 📚 參考來源
特點：純 Python，速度快（3-5s），但品質較低（只有 snippet 注入）

🗂️ 搜尋範圍

🔒 私有知識（Agent 專屬）

agents/{agent_id}-agent/knowledge/ ├── raw/ ← memory 自動寫入 └── wiki/ ← ingest 後結構化

🌐 全域知識（所有 Agent 共用）

knowledge/ ├── raw/ ← 預放原始資料 ├── wiki/ ← 3 篇競品分析 └── index.md ← 索引目錄
查詢順序：先私有 → 再全域 → 合併結果

⚡ 目前 Bot 運作狀態

Bot 有裝 kiro-cli → 99% 走路徑 A

WikiEngine 幾乎不被觸發（只在 kiro-cli timeout 或沒回覆時才 fallback）

kiro-cli 是否讀 wiki 由 AI 自行判斷，不受 Python 控制

🧠 kiro-cli 自身運作機制（進階）

核心概念：Skill 不是「全部」，而是「有就照做，沒有就自由發揮」。

啟動時載入的 Context

kiro-cli 收到訊息 ↓ 永遠載入（always in context）： • .kiro/steering/SOUL.md ← 人格（~200 字） • .kiro/skills/*/description ← 所有 Skill 觸發描述（~100 字/個） ↓ 內建 LLM 判斷：「匹配哪個 Skill？」 ↓ ├── ✅ 匹配 → 載入 SKILL.md 全文 → 照 SOP 執行 └── ❌ 無匹配 → 自由發揮（通用能力 + SOUL 人格）

三層載入模式（漸進式揭露）

層級何時載入大小內容
1. 後設資料 永遠在 context ~100 字/Skill name + description（觸發判斷用）
2. SKILL.md 本體 被觸發時 <500 行 完整執行指令
3. 附帶資源 SKILL.md 指示時 無限制 references/ scripts/ assets/
例：ark-competitor-brief 觸發時 Layer 1（已在 context）：description "競品 SWOT 簡報..." (~100 字) ↓ 判斷匹配 Layer 2（觸發後載入）：SKILL.md 全文（108 行） ↓ Step 7 需要 HTML 模板 Layer 3（按需載入）：references/swot-template.html（5KB）

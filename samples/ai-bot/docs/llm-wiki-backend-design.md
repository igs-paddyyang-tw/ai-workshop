## 1. 設計目標與定位

### 1.1 後台要解決的問題

Telegram 適合「即時通知 + 快速核准」，但不適合：

- 大量頁面的**瀏覽與比對**（長 diff、知識圖譜、批次審核）
- 知識庫**健康度的全貌掌握**（lint/schema/stale 統計趨勢）
- **檢索品質調校**（hybrid_search 權重、RAG 注入內容觀測）
- **回溯稽核**（誰在何時核准了什麼、log.md 的可視化）

後台網站定位為「**知識庫的維運駕駛艙**」：TG 負責推播與輕量決策，Web 負責深度管理；兩者共用同一套確認單（confirmation）資料，**在 TG 點過的單在 Web 即時同步狀態，反之亦然**。

### 1.2 使用角色

| 角色 | 權限 | 主要畫面 |
|---|---|---|
| Owner（Paddy） | 全部，含核准、刪除、設定 | 全部 |
| Maintainer（團隊成員） | 瀏覽、搜尋、發起 ingest、標註 | 除設定與刪除外 |
| Viewer / Agent（唯讀） | 瀏覽、搜尋 | Wiki 瀏覽、搜尋台 |

## 2. 資訊架構（IA）

```
知識庫後台（/kb）
├── ① 總覽 Dashboard                    ← lint + schema + 統計聚合
├── ② Wiki 瀏覽器（樹狀 + 閱讀器）        ← query
├── ③ 搜尋實驗台                        ← query + hybrid_search
├── ④ Ingest 工作台（蒸餾管線）          ← ingest
├── ⑤ 審核中心（確認單）                 ← confirmation_manager（與 TG 同步）
├── ⑥ 知識圖譜                          ← graph
├── ⑦ 品質中心                          ← lint + schema
├── ⑧ RAG 觀測台                        ← rag_bridge + QA 回饋
├── ⑨ 模板與 Schema 管理                 ← template + schema
└── ⑩ 來源與日誌                        ← sources.yaml + log.md + audit
```

8 個 Runtime Skills 與畫面的對應：**每個 skill 至少有一個主場畫面**，query/lint/schema 另以聚合形式出現在 Dashboard。

## 3. 十個畫面設計

### ① 總覽 Dashboard —「知識庫今天健康嗎？」

**目的**：30 秒掌握全庫狀態，異常一眼可見。

```

│ 專案切換 ▼ hermes        今日成本 $3.2/15   ⚙ 設定  👤     │
├──────────┬──────────┬──────────┬──────────┬────────────────┤
│ 總頁數    │ mature   │ stale    │ 待審單    │ 斷鏈/孤立頁    │
│  247     │  61%     │  12 ⚠️   │  3 🔔    │  2 / 5        │
├──────────┴──────────┴──────────┴──────────┴────────────────┤
│ 📈 頁面成長趨勢（30天）      │ 🍩 type 分佈  │ 🍩 status 分佈 │
├─────────────────────────────┴───────────────┴──────────────┤
│ 🕑 最近變更（log.md 最新 10 筆，附 cf_id / task_id 連結）    │
│ ⚠️ 待辦捷徑：3 張確認單待核 → ⑤ ｜ 12 頁 stale 待重驗 → ⑦   │

```

**資料來源**：`wiki_lint`（斷鏈/孤立）、`wiki_schema`（合法性統計）、index.md、log.md、confirmations 表。

### ② Wiki 瀏覽器 —「像 Obsidian 一樣讀知識庫」

**目的**：日常瀏覽、閱讀、輕量編修的主場。

```
┌───────────┬──────────────────────────────┬─────────────────┐
│ 📁 樹狀導覽 │  # Hermes Agent 資料查詢流程   │ Frontmatter 側欄 │
│ overview   │                              │ type: procedure │
│ ▸ concepts │  ## 摘要（TL;DR）             │ status: mature ●│
│ ▾ procedure│  每日 01:30 自動同步…          │ confidence: high│
│   · hermes-│                              │ last_verified   │
│     query  │  ## 內文                      │  2026-07-02     │
│ ▸ entities │  …每日自動同步一次 [src-0107]  │ sources(2) 🔗   │
│ ▸ decisions│   ↑ hover 顯示來源片段預覽     │ related(3) 🔗   │
│ 🔍 樹內篩選 │                              │ [歷史版本][編輯] │
└───────────┴──────────────────────────────┴─────────────────┘
```

**關鍵互動**：
- `[[wikilink]]` 可點擊跳轉；hover 顯示目標頁 TL;DR 預覽卡
- 來源標記 `[src-xxxx]` hover 顯示原文片段（溯源可視化，後台核心價值）
- status 徽章色碼：seedling 🌱 / developing 🌿 / mature 🌳 / stale ⚠️ / deprecated 🚫
- 「編輯」走確認單流程（人工編修也留稽核軌跡），非直接寫檔

### ③ 搜尋實驗台 —「調校檢索品質的實驗室」

**目的**：不只是搜尋框，而是能**比較不同檢索策略結果**的工具。

```
┌────────────────────────────────────────────────────────────┐
│ 🔍 [ hermes 同步頻率              ]  [搜尋]                  │
│ 模式：( ) query 基本  (●) hybrid_search  ( ) 兩者並排比較     │
│ 過濾：type ▼  status ▼(排除 deprecated ✓)  tags ▼            │
├──────────────────────────┬─────────────────────────────────┤
│ 結果（RRF 融合分數排序）    │ 並排比較模式時：                  │
│ 1. hermes-agent-overview  │  左欄 BM25 排名 vs 右欄融合排名    │
│    score 0.87 ｜mature    │  排名變化以 ↑↓ 標示               │
│    …命中片段 highlight…   │                                  │
│ 2. data-sync-frequency…   │                                  │
├──────────────────────────┴─────────────────────────────────┤
│ 每筆結果附：[開啟頁面] [看此頁被 RAG 引用的歷史] [👍👎標註相關性]│
└────────────────────────────────────────────────────────────┘
```

**進階**：相關性標註（👍👎）累積為檢索評測集，供日後調整 hybrid_search 權重與回歸測試（對應規格文件的「RAG 命中率 ≥ 85%」KPI）。

### ⑤ 審核中心 —「TG 確認單的桌面版，適合大 diff」

**目的**：與 TG Inline Button 同一套確認單，但提供 TG 給不了的**完整 diff 檢視與批次操作**。

```
┌──────────────┬─────────────────────────────────────────────┐
│ 待審清單      │ cf-000131  📥 Ingest ｜batch b-0130          │
│ ● cf-000131  │ ┌────────── 變更預覽（分頁籤）──────────┐     │
│   ingest 🔔  │ │ [新增 8] [合併 2] [更新 1] [衝突 1]    │     │
│ ● cf-000132  │ │ 更新：hermes-agent-overview            │     │
│   conflict ⚡ │ │  - 每日 02:00 同步        （紅，刪除）  │     │
│ ○ cf-000128  │ │  + 每日 01:30 同步 [src-0113]（綠，新增）│     │
│   已核准 ✅   │ └────────────────────────────────────────┘     │
│              │ 逐項勾選 ☑☑☑☐ →可部分核准                     │
│ 篩選：kind ▼  │ [✅ 核准勾選項] [❌ 全部拒絕] [✏️ 附註退回修改]  │
```

### ⑥ 知識圖譜 —「知識庫的地圖」

**目的**：`wiki_graph` 的力導向視覺化，找 hub、孤立頁與知識空洞。

```
┌────────────────────────────────────────────────────────────┐
│ 視角：(●)全庫 ( )以某頁為中心(2階) ( )依tag分群              │
│                      ┌────┐                                 │
│         ○──────○────│hub ●│────○     節點大小=連入數         │
│        孤立○         └────┘   ＼○    顏色=type              │
│                                      邊=wikilink            │
│ 側欄：點節點 → TL;DR 預覽 + [開啟頁面]                        │
│ 底部：⚠ 孤立頁 5（一鍵列出）｜🔗 斷鏈 2（指向不存在的頁）      │
└────────────────────────────────────────────────────────────┘
```

**維運價值**：孤立頁多 = 蒸餾時 Linker 沒建好連結；某 tag 群完全無節點 = 知識空洞，可轉為 ingest 需求。

### ⑦ 品質中心 —「lint + schema 的體檢報告與修復台」

**目的**：把 `wiki_lint` / `wiki_schema` 從 CLI 報告變成可操作的工作清單。

```
┌────────────────────────────────────────────────────────────┐
│ [▶ 立即全庫體檢]   上次體檢：今日 02:30（排程）               │
├───────────────┬────────────────────────────────────────────┤
│ 問題分類       │ 問題清單（可勾選批次處理）                    │
│ frontmatter    │ ☐ concepts/xxx.md 缺 last_verified          │
│  缺欄位 (7)    │   [🤖 請 Agent 修復] [✏️ 手動修] [🙈 忽略]    │
│ schema 非法值(2)│ ☐ type: "howto" 非法 → 建議改 procedure     │
│ 斷裂連結 (2)   │ ☐ [[old-page]] 目標不存在 → 建議改連結/建頁   │
│ 孤立頁 (5)     │                                             │
│ stale >180d(12)│ ☐ …一鍵發起「重驗任務」→ 走 ingest 管線       │
├───────────────┴────────────────────────────────────────────┤
│ 📈 健康分數趨勢（每日體檢分數折線，退步即告警到 TG）           │
└────────────────────────────────────────────────────────────┘
```

「🤖 請 Agent 修復」= 開任務給 librarian-agent，修復結果照樣走確認單。

### ⑧ RAG 觀測台 —「rag_bridge 到底注入了什麼？」

**目的**：讓隱性運作的 rag_bridge 可觀測、可歸因、可改進。

```
┌────────────────────────────────────────────────────────────┐
│ 問答紀錄（來自 TG / API / MCP 三通道，通道以圖示區分）         │
│ ┌──────────────────────────────────────────────────────┐   │
│ │ qa-000871 📱TG  「Hermes 多久同步一次?」    👍          │   │
│ │  ├ 注入 context：hermes-agent-overview(0.87)、…(0.61) │   │
│ │  ├ 回答全文 + 引用頁面                                  │   │
│ │  └ [此答案引用的頁面是否過期?] [加入評測集]              │   │
│ └──────────────────────────────────────────────────────┘   │
│ 統計：命中率、無答案率、👎 率（按週）；👎 集中的主題 TOP5      │
│  → 👎 熱區 = 知識缺口，可一鍵轉 ingest 需求                   │
└────────────────────────────────────────────────────────────┘
```

**這一頁是後台的差異化價值**：TG 只看得到單次問答，這裡看得到檢索品質的系統性問題。

### ⑨ 模板與 Schema 管理 —「知識庫的憲法」

**目的**：管理 `wiki_template` 頁面模板與 schema.md 規則。

- 模板列表（entity / concept / procedure / decision / faq…）＋ Markdown 即時預覽
- Schema 編輯器：type/status 合法值、必填欄位定義；**變更 schema 需走確認單**，並自動觸發全庫 schema 重驗（顯示「此變更將使 N 頁不合規」的影響預估）
- taxonomy 樹編輯（新增頂層分類 = 人工核准點）

---

### ⑩ 來源與日誌 —「稽核與溯源的總帳」

- **來源管理**：sources.yaml 表格化（src_id、檔名、hash、日期、被引用頁數）；點 src → 反查所有引用它的頁面；原始檔預覽
- **操作日誌**：log.md + audit_logger 時間軸，可依 agent / cf_id / task_id 過濾；每筆變更可展開當時 diff
- **匯出**：知識庫快照打包下載（zip）、log CSV 匯出

## 4. 畫面 × Skill × API 對照表

| 畫面 | 主要 Skills | 主要 API（既有/新增） |

## 5. 技術與視覺規範

| 面向 | 決策 |
|---|---|
| 前端 | 沿用 apps/web 既有技術棧；暗黑科技風（對齊 ark-wiki-engine 既定風格） |
| Markdown 渲染 | 支援 wikilink 解析、frontmatter 抽出至側欄、`[src-xxxx]` hover 溯源卡 |
| 圖譜 | d3 力導向；>500 節點時預設切換「以頁為中心 2 階」視角避免效能問題 |
| 權限 | 沿用 gateway auth；核准操作僅 Owner；所有寫入走確認單，Web 不繞過 |
| 響應式 | 桌面優先；⑤ 審核中心提供窄版（與 TG 互補的行動網頁快審） |

## 6. 開發優先序（建議三期）

| 期別 | 畫面 | 理由 |
|---|---|---|
| P1（MVP，2 週） | ② Wiki 瀏覽器、⑤ 審核中心、① Dashboard 簡版 | 讀 + 審 + 看狀態是最小可用閉環；⑤ 直接複用確認單資料 |
| P2（2 週） | ④ Ingest 工作台、⑦ 品質中心、③ 搜尋實驗台 | 補齊生產線與品質維運 |
| P3（2 週） | ⑥ 知識圖譜、⑧ RAG 觀測台、⑨ 模板管理、⑩ 來源日誌 | 進階觀測與治理（對應你表格中的「進階」skills：graph / hybrid_search / template / schema 深度功能） |

> 對照你現況：query/ingest 已熟（03 教過）→ P1/P2 畫面主要是把已會的東西可視化，風險低；lint 只被提過一行 → ⑦ 品質中心正好把它變成日常工具；graph/hybrid_search/template/schema 未教 → 排 P3，讓後台開發順便成為團隊學習這四個進階 skill 的載體。

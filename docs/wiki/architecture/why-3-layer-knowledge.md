# 為什麼用三層知識庫（私有 → 共用 → 專案）

## 問題背景：Kiro CLI 的 cwd 限制

Kiro CLI 啟動時以 `process.cwd()` 為根目錄，所有檔案操作都受限於該目錄。
這代表：

- Agent 只能「看到」啟動目錄以下的檔案
- 多個 Agent 若在不同專案目錄啟動，彼此的知識庫互不可見
- 若把所有知識集中到一處，又會造成單一 Agent 載入過多無關內容

**核心矛盾**：知識需要共享，但執行環境強制隔離。

## 設計決策：相對路徑 `../../` 突破邊界

我們選擇「約定優於配置」的方式：

```
專案根目錄/
├── .kiro/
│   └── wiki/              ← Layer 3: 專案知識（最高優先）
├── ../../shared/
│   └── wiki/              ← Layer 2: 共用知識（跨專案共享）
└── ~/.ark/
    └── wiki/              ← Layer 1: 私有知識（個人筆記、密鑰備忘）
```

每個 Agent 啟動時，WikiEngine 依序掃描三層路徑，用相對路徑 `../../shared/wiki` 向上跳出 cwd 限制，不需要額外的 symlink 或環境變數。

## 三層查詢優先級

| 優先級 | 層級 | 路徑 | 用途 |
|--------|------|------|------|
| 🥇 最高 | 專案層 | `.kiro/wiki/` | 該專案的 domain context |
| 🥈 中等 | 共用層 | `../../shared/wiki/` | 團隊共享的 SOP、API 文件 |
| 🥉 最低 | 私有層 | `~/.ark/wiki/` | 個人偏好、私密備忘 |

查詢時 **由上而下搜尋，同名文件高層覆蓋低層**（shadow 機制）。
這讓專案可以 override 共用知識，而不需要複製整份文件。

## 實際結構圖

```
┌─────────────────────────────────────────┐
│          WikiEngine.search(query)        │
└─────────────┬───────────────────────────┘
              │ 合併三層 index
              ▼
┌─────────────────────┐
│ Layer 3: 專案知識    │  ← .kiro/wiki/ (git tracked)
│ 優先級最高，覆蓋下層  │
├─────────────────────┤
│ Layer 2: 共用知識    │  ← ../../shared/wiki/ (git submodule)
│ 團隊級別，多專案共用  │
├─────────────────────┤
│ Layer 1: 私有知識    │  ← ~/.ark/wiki/ (不進 git)
│ 個人筆記，最低優先    │
└─────────────────────┘
```

## 設計效益

1. **零配置**：約定路徑，clone 即可用
2. **漸進擴展**：單人開發只需 Layer 3，團隊再加 Layer 2
3. **安全分層**：私密資訊永遠不進 git
4. **Shadow 覆蓋**：專案可局部覆寫共用知識，無需 fork

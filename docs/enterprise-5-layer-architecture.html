我們將 AI 團隊的管理職責徹底解耦。全新架構不僅涵蓋入口、系統調度與團隊協作，更將「知識與技能」獨立為底層 DNA。Agent 每次執行任務、反思，都將為整間公司累積可重用的程式化技能。

1 宏觀定義：企業級 AI 五層架構（The Five-Layer Stack）

此五層架構解決了過往 AI 系統「無狀態、無法累積經驗、各模組耦合過深」的痛點。以下為由上至下的執行與控制流向：

Layer 1: Entry & API Gateway (入口與傳輸層)
OpenClaw Gateway
負責協議轉譯：Telegram / Web / Plane Board / GitHub Webhooks / MCP 接口。不涉入任何專案邏輯。
Layer 2: AI Team OS (作業系統調度層)
Multica Platform
Sprint & Board 同步 Runtime Registry Event Bus 廣播 Runtime Manager
Layer 3: Agent Group Collaboration (團隊協作與解耦層)
CrewAI Engine
Leader Agent (任務拆解/決策) Worker Agent Group (協同產出)
Layer 4: Execution Runtime (認知與執行環境層)
Hermes Agent / Kiro CLI / Claude Code / Codex
無狀態（Stateless）執行端，專注於當下任務。提供 Think → Code → Reflect 反思循環。
Layer 5: Knowledge & Skill Evolution (知識與技能演化層)
Skill LLM Wiki & GitHub Repositories
skill.md (宣告式提示技能) GitHub Git-backed

部門與群組：CrewAI 企業級階層模型

為了避免 Multica 單一節點承擔過多壓力，我們將 Leader 與 Worker 職責徹底劃歸為 **CrewAI (Layer 3)**。 Leader 本身即是 Agent，負責分析與任務指派；而 Worker 則是專業的執行單元。在遊戲研發情境下，我們切分為以下四大專業 Crew：

  • Multica OS
    • Game Dev Crew
      • Dev Leader Agent
        • Planner (Kiro)
        • Frontend (Hermes)
        • QA Agent (OpenClaw)
    • AIBI Crew
      • BI Director Agent
        • Revenue Leader
        • Retention Worker

Layer 5: 技能與知識庫的自演化機制（Self-Evolution）

基於 Git 的 Skill Wiki 治理

我們打破了過往「人工手寫單行提示詞」或「過度僵硬的 YAML 格式」舊思維。在五層架構中，採用 Markdown 宣告（Skill as Markdown），並託管於 GitHub，其自演化治理邏輯如下：

1. designer-agent 完成黃金鯊魚外觀設計
↓ 自動記錄設計決策到 knowledge/raw/
2. coder-agent 實作遊戲邏輯並通過 qa 驗收
↓ 實作經驗寫入 SKILL.md（倍率公式+限時機制）
3. ingest 自動匯入 → Wiki 知識成長
↓ 下次類似需求能引用本次經驗
4. 全團隊解鎖「新增 Boss」的標準流程與參考規格

SKILL.md 宣告式規格範例（Boss 設計技能）

採用 Front-matter 結構結合結構化 Markdown，方便 LLM 做語意解析與自動觸發： 

---
name: "ark-boss-designer"
version: "1.0.0"
author: "designer-agent"
dependencies:
  - "kiro-cli >= 2.7"
  - "gemini-api"
review_status: "approved"
tags: ["game-design", "fishing-game", "boss"]
---

# 技能：捕魚機 Boss 設計 (ark-boss-designer)

## 1. 觸發情境 (Triggers)
* **關鍵字**：「新增 Boss」「設計魚種」「Boss 規格」
* **輸入格式**：Boss 名稱 + 倍率 + 出場條件

## 2. 執行步驟
1. 分析現有 Boss 列表（避免重複風格）
2. 設計外觀：配色、體型、特效、動畫
3. 設計機制：血量公式、倍率、限時、特殊技能
4. 產出規格文件（含美術參考和數值表）

## 3. 驗收條件
* **美術**：風格與現有 Boss 一致但可辨識
* **數值**：模擬 1000 局爆率偏差 ≤ ±2%
* **體驗**：限時機制不超過 60 秒

## 4. 參考案例
- 黃金鯊魚：10000x / 30 秒 / 金光出場特效
- Ocean King 3 Flaming Dragon：7 波龍浪攻擊

五層事件驅動生命週期：開發新魚種「黃金鯊魚 Boss」

1

L1 入口層 (Telegram Gateway) 接收需求

企劃在 Telegram 輸入 /assign 新增黃金鯊魚 Boss：10000x 倍率、限時 30 秒出現、需要專屬出場動畫和受擊特效。Gateway 接收並轉發給 pm-agent。

2

L2 協作層 (TaskGraph) 任務拆解與分派

pm-agent 分析需求複雜度，拆解為三個子任務：「外觀設計」指派 designer-agent、「遊戲邏輯實作」指派 coder-agent、「爆率測試驗收」指派 qa-agent。TaskGraph 標記依賴：coder 等 designer 完成後開始，qa 等 coder 完成後開始。

3

L3 執行層 (Agent Runtime) 各 Agent 執行任務

designer-agent 產出黃金鯊魚外觀設計稿：金色鱗片、紅色眼睛、出場時全屏金光特效、受擊時碎裂粒子動畫。產出格式化的設計規格文件。

4

L4 執行層 (Kiro CLI + Gemini) 編碼與測試

coder-agent 根據設計稿實作遊戲邏輯：血量公式 HP = base × level_factor、10000x 倍率計算、30 秒限時計時器。qa-agent 接手後模擬 1000 局射擊，驗證爆率偏差在 ±2% 以內，輸出測試報告。

5

L5 知識層 (Wiki + Memory) 知識沈澱與自演化

任務完成後，設計規格、實作邏輯、測試報告自動寫入 knowledge/raw/golden-shark-boss.md。下次 ingest 後進入 Wiki。往後企劃再提「新增 Boss」需求時，Agent 能引用本次經驗：倍率公式、限時機制、測試方法，品質越來越穩定。耗時 12 min / 費用 $0.08 / 3 Agent 協作。

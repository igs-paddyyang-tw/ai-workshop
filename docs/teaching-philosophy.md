# AI Workshop 教學理念

## 一句話

> 不教你寫程式，教你「駕馭 AI」— 用自然語言設計系統、用結果驗證品質。

---

## 為什麼這樣教

### 傳統 AI 教學的問題

| 問題 | 結果 |
|------|------|
| 從理論開始（Transformer / Attention） | 學員聽不懂就放棄 |
| 手把手敲程式碼 | 離開教室就不會了 |
| 用 Jupyter Notebook 跑 demo | 跟實際業務無關 |
| 教一堆工具但沒串起來 | 學了 5 個工具但做不出一個產品 |

### 我們的做法

| 原則 | 做法 |
|------|------|
| **體驗先於理解** | 先跑起來、先看到效果，再解釋為什麼 |
| **結果先於過程** | 先在 Telegram 看到 Bot 回話，再看程式碼怎麼寫的 |
| **設計先於實作** | 先想清楚 SOUL 要什麼風格，再讓 AI 產出 |
| **帶走先於教完** | samples/ 是完整可跑的，帶走就能用在業務 |

## 兩個核心工程思維

### 🏗️ 駕馭工程（Steering Engineering）— 課程 A

**定義**：你設計方向，AI 執行細節。

傳統開發：
```
你想 → 你寫 → 你測 → 你修 → 你部署
```

駕馭工程：
```
你想 → 你告訴 AI → AI 做 → 你驗證 → 你調整方向
```

| 你的角色 | AI 的角色 |
|---------|----------|
| 設計 SOUL（人格） | 依 SOUL 產出回應 |
| 拷問需求、決策 | 依決策產出 Spec |
| 確認 Spec 正確 | 依 Spec 產出程式碼 |
| 丟入知識素材 | 建立 RAG 索引 |
| 驗證結果品質 | 自動修正直到 Score ≥ 90 |

**核心心法**：
- 你是方向盤，AI 是引擎
- 駕馭 ≠ 放手，駕馭 = 你決定去哪
- 不是「AI 幫你寫程式」，是「你設計系統，AI 是你的執行力」
- 知識累積也是駕馭 — 你決定「什麼知識值得留下」，AI 負責整理和索引

**知識駕馭循環**：
```
你丟素材（raw/）→ AI 整理成知識頁面（wiki/）→ 你驗證品質
  → 知識庫越來越厚 → Agent 回答越來越準 → 你再丟更多素材 → ♻️
```

駕馭的不只是「行為的方向」（SOUL），也是「知識的方向」（Wiki）。

**反面教材**：
- ❌ 全部交給 AI 不看結果 → 失控
- ❌ 什麼都自己來不用 AI → 沒效率
- ❌ 不質疑 AI 的產出 → 品質隨機

---

### 🔄 迴圈工程（Loop Engineering）— 課程 B

**定義**：設計迴圈，不是設計步驟。讓系統自己跑、自己學、自己成長。

線性思維：
```
需求 → 開發 → 交付 → 結束
```

迴圈思維：
```
需求 → 執行 → 產出 → 記憶 → 知識成長 → 下次更準 → ♻️
```

| 線性（課程 A） | 迴圈（課程 B） |
|--------------|--------------|
| 你 /assign → Agent 做一次 | 排程自動觸發 → 每天做 |
| 你加知識 → Agent 能回答 | Agent 自己累積記憶 → 越來越準 |
| 一個 Agent 做一件事 | 一群 Agent 分工 → 結果互相依賴 |
| Demo 等級 | 生產等級 |

**核心心法**：
- 設計迴圈，不是設計步驟
- 每次執行都要讓系統「學到東西」
- 無人值守 = 排程 + 費控 + 監控 + 自演化

**三層遞進**：
```
本地迴圈（一台機器上的 Agent 團隊自轉）
  → 跨機迴圈（多台機器互相派工、互相學習）
  → 自演化生態（專家系統 ↔ 開發平台雙向供給）
```

**自演化循環**（對齊實際實作）：
```
對話 → memory 自動記錄（agents/*/knowledge/raw/）
    → 定期 ingest → wiki/ + .index/ 四層搜尋索引重建
    → query 走 metadata精確 → BM25索引 → hybrid混合 → rerank
    → Agent 回答精準度 ↑
    → 使用者信任度 ↑ → 問更多問題
    → memory 更多 → ingest 更多 → Wiki 更厚 → ♻️
```

**從 A 到 B = 從「你踩油門」到「自動駕駛」**：

```
課程 A 的迴圈是「手動驅動」：
  02: 你觸發驗證 → Score < 90 → 你說「修」→ AI 修 → 再驗 → Score ↑
      每次循環品質收斂，但需要你手動踩油門。

課程 B 的迴圈是「自動驅動」：
  05: 排程觸發 → Agent 執行 → 記憶累積 → 下次更準 → 排程再觸發
      系統自己跑，你只需要看 Dashboard 確認沒出事。
```

學員在 02 已經體驗到「迴圈讓品質收斂」，到 05 理解「把迴圈自動化 = 無人值守」。

## 教學設計原則

### 1. Vibe Coding — 自然語言操作（雙軌）

學員不需要寫程式碼。操作有兩個入口，服務兩種人：

| 入口 | 對誰 | 做什麼 |
|------|------|--------|
| 📝 Kiro IDE | 軟體人 | 修 SOUL、開發 Skill、調架構、管知識庫 |
| 📱 Telegram Bot | 非軟體人 | 使用 Agent、查知識、派工、看報告 |

```
📝 Kiro IDE 輸入：「把 SOUL 改成幽默風格」
→ AI 自動修改程式碼
→ 📱 Telegram 驗證效果
```

**為什麼雙軌**：
- 一個 Workshop 同時服務「做的人」和「用的人」
- 軟體人學「怎麼打造」，非軟體人學「怎麼駕馭」
- 兩者都是自然語言操作，門檻一樣低

### 2. 前半 Kiro + 後半 Telegram

每堂課都是：

```
前半段（Kiro IDE）：開發者視角 — 設定、建構、確認功能正確
後半段（Telegram）：使用者視角 — 驗證上線效果 = 第三方可用
```

**為什麼這樣分**：
- 開發 OK ≠ 上線 OK（你自己測過不代表使用者也行）
- 有明確的「開發完成 → 上線驗證」分界線
- 模擬真實工作流程：開發 → QA → 上線

### 3. 完成度分級

每堂課都有三級：

| 等級 | 意義 | 時間 |
|------|------|------|
| 🎯 保底 | 最低可接受（系統能跑） | 15 min |
| ✅ 標準 | 課堂目標達成 | 35 min |
| 🏆 快速 | 進階探索（快的人有事做） | 50 min |

**為什麼這樣設**：
- 學員速度不同，不能讓快的人等慢的
- 保底確保每個人至少有成就感
- 快速的人有挑戰，不會無聊

### 4. 失敗處理 ⚠️

每個 Step 都有「如果不成功」的處理方式：
- 不是「請找講師」
- 是具體的排查步驟 + Kiro 修復指令
- 學員能自己解決 80% 的問題

### 5. 帶走就能用

`samples/` 不是「教學用的簡化版」，是**完整可跑的產品級程式碼**：

| samples/ | 特色 |
|----------|------|
| ai-bot | 8 Agent + 四層搜尋 Wiki + A2A 跨機派工 + Web UI 6 頁 |
| ai-team-agent | 5 Agent + DAG 派工 + Scheduler + 費控 + 自演化知識循環 |

學員回去只需要：
1. 改 SOUL → 符合自己公司的風格
2. 改 knowledge/raw/ → 放自己公司的文件
3. 改 team.yaml → 調整團隊組成

## 貫穿案例設計

### 為什麼選「遊戲競品分析」

| 理由 | 說明 |
|------|------|
| 跟公司業務相關 | 學員是遊戲公司的人 |
| 有具體產出物 | 競品報告、設計分析、提案書 |
| 能串接五堂課 | 從 SOUL 設計 → Wiki 知識 → Team 分工 → 排程自動 |
| 有趣不無聊 | 比「TODO App」有意思 |

### 案例在每堂課的呈現

```
01: 設計「遊戲分析師」的 SOUL
02: 開發新聞爬蟲 Skill（市場資訊蒐集）
03: 匯入 Ocean King / Super Ace 競品分析到 Wiki
04: market + designer + report 協作產出「捕魚機競品報告」
05: 排程每天科技日報 + 每週競品週報
```

## 兩個產品的教學定位

### 不是升級關係，是供應鏈

| | 🏗️ AI Agent 專家系統平台（ai-bot） | 🔄 AI Agent 遊戲開發平台（ai-team-agent） |
|---|---|---|
| **教什麼** | 鍛造 Agent 能力（SOUL + Skill + Wiki） | 讓 Agent 團隊自動跑出成果 |
| **人的角色** | 方向盤 — 深度介入、反覆調整 | 監督者 — 設計好迴圈後觀察 |
| **產出** | 成熟的能力資產（可搬運、可複用） | 業務成果（報告、程式碼、遊戲） |

```
專家系統（鍛造廠）──蒸餾能力資產──→ 遊戲開發平台（生產線）
        ↑                                       │
        └─── 回饋問題，重新磨刀 ←───────────────┘
```

**不是「A 學完才能學 B」**，而是「A 產出的東西供 B 消費」。兩個課程完全獨立授課，但學員如果兩個都學，會理解它們之間的供應鏈關係。

### 為什麼架構一樣

兩個產品的程式碼架構完全相同（coordinator / runtime / gateway），差異只在：
- 放了什麼 Agent（不同的 SOUL + Skill）
- 有沒有 team.yaml（個體 vs 團隊）
- knowledge/ 裝了什麼（不同領域知識）

**教學意義**：
- 學一套架構，兩邊都會用
- 專家系統蒸餾的 Agent 能力（agents/ 資料夾）直接搬到遊戲開發平台
- 遇到問題隨時回專家系統調整，不需要適配
- 學員不會有「從 A 換到 B 要重學」的斷裂感

---

## 課程獨立性設計

### 完全獨立

- 課程 A 不需要先上課程 B
- 課程 B 不需要先上課程 A
- 每個課程有自己的 sample、自己的 QUICKSTART、自己的 build-guide

### 但有銜接

如果兩個都上：
- A 學會設計個體 Agent → B 學會讓一群 Agent 合作
- A 的 knowledge/ 知識 → B 的 Agent 也能引用
- A 的 SOUL 設計能力 → B 加新 Agent 時直接用

---

## 不教什麼

| 不教 | 為什麼 |
|------|--------|
| Transformer 原理 | 跟「用 AI」無關 |
| 手動寫 Python 程式碼 | 有 Kiro IDE，不需要 |
| Prompt Engineering 技巧 | SOUL + Skill 取代了碎片化 prompt |
| 雲端部署（AWS/GCP） | 超出 50 min 範圍，放回家練習 |
| 模型微調（Fine-tuning） | 用 RAG + Skill 就夠了 |

---

## 成功標準

一堂課成功 = 學員帶走 3 件事：

1. **一個能用的東西**：samples/ 直接帶走跑
2. **一個思維方式**：駕馭工程 or 迴圈工程
3. **一個「我會了」的感覺**：不是「我聽懂了」，是「我做到了」

---

*教學的目標不是讓學員「學到很多」，而是讓學員「帶走能用的」。*
